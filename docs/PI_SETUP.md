# Raspberry Pi Home Server Setup

## Goal

Turn the Raspberry Pi 5 into a general-purpose personal home server - a substrate for deploying anything (Dockerized or not), not just DailyNiche. DailyNiche's staging deployment (CLAUDE.md's Phase 9) is the first thing to run on it, but the setup here is deliberately not DailyNiche-specific, so future projects can land on the same box without redoing this work.

- Headless setup planned - no monitor/keyboard, WiFi network
- Dev machine (this one) not yet confirmed to have an SSH keypair - check before Phase A

  - **How this works, conceptually** (added 2026-08-18, for future reference since none of this is obvious from the commands alone):
    - **Why this survives the Pi moving networks at all:** normally, exposing a home-network service to the internet means port-forwarding on the router - often impossible on mobile hotspots/CGNAT anyway. Cloudflare Tunnel flips the direction: `cloudflared` running *on the Pi* makes an **outbound** connection to Cloudflare's edge and holds it open. Nothing is opened inbound on any router. When a request for `ssh.imkaem.xyz` arrives at Cloudflare's edge, it gets forwarded down that already-open tunnel to the Pi. The tunnel doesn't care what IP the Pi currently has, only that it can reach the internet - which is exactly why this fixes the recurring "Pi changed networks, now unreachable" problem.
    - **Why `service: ssh://localhost:22` reaches the real Pi, not a container:** the `cloudflared` container runs with `network_mode: host` (see C.4 above), which throws away Docker's normal network isolation and makes the container share the host's network stack directly. So `localhost` *inside* the container is the Pi itself, and port 22 is the Pi's real sshd.
    - **What `cloudflared tunnel route dns ... ssh.imkaem.xyz` actually did:** created a DNS CNAME record pointing that hostname at the tunnel. Without it, the ingress rule would exist but the hostname simply wouldn't resolve to anything.
    - **Why the client needs `cloudflared` too, and what `ProxyCommand` does:** `cloudflared access ssh --hostname ssh.imkaem.xyz` is a small program that authenticates to Cloudflare and speaks raw SSH bytes over its own stdin/stdout, tunneled to the Pi. SSH's `ProxyCommand` option tells the `ssh` client "don't open a normal TCP socket - run this program instead, and treat its stdin/stdout as the connection." Regular `ssh` has no idea the "socket" it's talking to is actually a process routing through Cloudflare's global network rather than a direct connection - it's a transport swap that's otherwise fully transparent.
    - **Why the client install skipped `sudo`/apt:** a `.deb` file is just an archive; `dpkg-deb -x` extracts its contents without running the installer or needing root. Cloudflare's apt repo also didn't yet support this laptop's (very new) Ubuntu release, so extracting the binary from the official GitHub-released `.deb` into `~/.local/bin` (already on `PATH`) sidestepped both problems at once.
